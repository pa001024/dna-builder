# 线上构筑 DPS 复现与消融分析

## 0. 心智模型

```
线上分享构筑 (GraphQL charSettings JSON)
        │
        ▼
normalizeCharSettings ──> createCharBuildFromSettings(charId, settings) ──> build.calculate()
                                                                              │
                                          ┌───────────────────────────────────┴────────────┐
                                    targetFunction（综合DPS 等）              customVariables 逐条求值
```

- **不要手算面板**。所有数值都必须从模型跑出来，攻略文案里的每个数字都要能追溯到一次 `calculate()`。
- 消融（ablation）是核心手法：**改一个变量 → 重算 → 记录 Δ%**。这比"这件东西很强"有说服力得多。

## 1. 拉取线上构筑

```bash
bun .agents/skills/build-creator/scripts/fetch-online-builds.ts list <charId>           # 元数据列表（含 id），落 .tmp/online-builds/list-<charId>.json
bun .agents/skills/build-creator/scripts/fetch-online-builds.ts download <id> [id...]  # 单拉配装，charSettings 落 .tmp/online-builds/<id>.json
```
详见 build-creator 技能

## 2. 本地复现

写成 `.tmp/*.ts`，用 `bun` 跑（`bun` 会读 tsconfig 的 `@/*` paths，相对路径 import 也可以）。
**bun 直接读仓库里的 `src/data/d/*.data.ts` 真实数据**，不受 dev server 数据包重写影响。

```ts
import { normalizeCharSettings } from "../src/composables/useCharSettings"
import { createCharBuildFromSettings } from "../src/data/CharBuildHelper"
import { charMap, modMap, petMap, weaponMap } from "../src/data"
import raw from "./build_xxx.json"

const BASE = JSON.parse((raw as any).data.build.charSettings)

/** 按补丁重算；表达式引用失效时返回 NaN 而不是抛栈。 */
function calc(patch: Record<string, any> = {}) {
    try {
        return createCharBuildFromSettings(3104, normalizeCharSettings({ ...BASE, ...patch })).calculate()
    } catch {
        return Number.NaN
    }
}
const D0 = calc()   // 基线

// 逐条 customVariables 求值（拆伤害构成）
const b = createCharBuildFromSettings(3104, normalizeCharSettings(BASE))
for (const [name] of BASE.customVariables) console.log(name, b.calculateTargetFunction(undefined, name))
```

- `createCharBuildFromSettings(charId, settings)` 的第三/四参数是 `inv`（背包快照）与 `timeline`，线上构筑一般不用传。
- 属性面板用 `build.calculateWeaponAttributes()`（含武器转化项，如充盈威力）；只要角色侧用 `build.calculateAttributes()`。
- 地图/名称映射：`modMap` / `weaponMap` / `charMap` / `petMap` 都是 **Map**，用 `.get(id)`。

## 3. 消融维度（按这个顺序做，覆盖最常被问的点）

| 维度 | 补丁字段 | 备注 |
|---|---|---|
| 单条 BUFF | `buffs: BASE.buffs.filter(...)` | 逐条撤，排序输出；组内多条要**分组撤**（有重叠，别把单条 Δ 相加） |
| 队友 | 同上，按「哪些 BUFF 来自哪个队友」分组 | 队友槽位 `team1/team2` 与队友武器**对 DPS 无影响**，收益全在挂的 BUFF 上 |
| 魔灵 | `petId: 0`（去被动+主动）、`traits: []`（去潜质）、`petCoverage: 0~1` | 魔灵 BUFF 由 `CharBuildHelper` 自动注入，**不在 buffs 列表里** |
| 武器 | `meleeWeapon` / `rangedWeapon` | 见 §4 命名空间陷阱 |
| 魔之楔 | `charMods` / `meleeMods` / `rangedMods` 数组内替换或置 `null` | 置 `null` 表示空槽 |
| 中枢 | `auraMod` | **不能设 0**（会 `MOD ID "0" 未在静态表中找到`），要么不传，要么换真实 id |
| 面板 | `resonanceGain`（**和鸣增益**）、`charLevel`、`charSkillLevel`、`hpPercent`、`enemyResistance`、`enemyLevel` | 敏感性扫描是攻略"养成优先级"章节的素材 |

分组策略：先按来源分组（队友 A 组 / 队友 B 组 / 自身溯源组 / 魔灵），再在组内做单条排序。报告的措辞要区分「撤掉这一组 −X%」与「单条 −Y%」。

### 流派判定（技能流 / 武器流）

⚠️ **口径**：这两个词指**辅助（队友）配置**，**不是武器选择**。同一角色的两派很可能**武器完全相同**——换的是队友，以及随之联动的 2~3 条 MOD。曾按"技能伤害 vs 武器伤害"去理解，答出了一版错结论。

1. **先横向比 `buffs`，不是先比武器**：`buildsCount(charId)` + `builds(charId, limit: 100)` 拉全量，逐份解析 `charSettings.buffs`，按前缀把 BUFF 归到队友身上（`扶疏*` / `卡米拉*` / `菲娜*` / `松露*` / `榛子*`），队伍构成立刻可见。
2. **增益取向决定流派**（看 `buff.data.ts` 的字段名，别靠名字猜）：
   - **技能侧辅助**（扶疏 / 卡米拉）：给 `技能伤害` `技能威力` `技能速度` `技能无视防御` → 强化**技能**。
   - **武器侧辅助**（菲娜 / 松露与榛子）：给 `武器伤害` `攻击` `增伤` `属性穿透` `背水` → 强化**武器伤害**。
3. **配装随流派联动**（实测全局只差 2~3 处）：
   - 近战槽：技能流 `穿花刺骨`（改双刀滑铲招式）／武器流 `时运`（按连击等级提触发概率）。
   - 角色槽：技能流堆 `涅槃·决断`×4（技能威力 +30% / 生命 +72%，`契约者` 系列可重复装备）／武器流带 `全盛·追袭`（**技能伤害 −50%** 换武器追加伤害，取向正好相反）。
4. **量化要同时给循环与结构**：`calculate()` 出总 DPS，再取 `循环用时` + 各伤害项占比。**技能流的特征是循环短、技能侧占比高**（法露茜实测：1.52s / 64.6% vs 武器流 2.73s / 15.6%）。技能流总 DPS 通常更低（48 亿 vs 66 亿），它的卖点是节奏不是数字，报告不能只甩 DPS。
5. **做交叉矩阵验证是否配套**：固定 MOD，只把 `buffs` 里的辅助组换成另一套，4 格跑完（法露茜实测：技能 MOD × 技能辅助 **48.423** ／ × 武器辅助 **77.889**；武器 MOD × 技能辅助 **28.655** ／ × 武器辅助 **66.037**）。矩阵能直接说明"技能流辅助在任何 MOD 下都更低"这类结论。
   ⚠️ 但**矩阵最优格未必是「同流派配对」**（上例 技能流 MOD ＋ 武器流辅助 = 77.889，高于两份线上原稿）—— 要断言"混搭更强"，必须另配一套**可导入的 BD** 并做回环校验（见下），不能只靠换 BUFF 的实验下结论。

### 手法（循环）建模

当问题从「这套配装多少」变成「这套手法多少」时，`customVariables` 里的 `循环用时` / `[羽化]触发周期` 只是**作者自定的替代式**，不能照抄。做法是**自建逐秒速率模型**，把上限约束显式写出来：

> ⚠️ **先确认手法在游戏里做得出来，再谈数值**。近战连招受**连段顺序**约束：连续按攻击键只会跑 `1234 → 1234` 的循环，**不能人为「只打前两段再从头开始」**。所以近战序列只能是 `(1234)^n ＋ 收尾残段（1 / 2 / 3 段）`，候选集里**禁止**出现 `123123`、`121212` 这类组合。曾按 `一二三×2` 扫出"最优解"，实际打不出来（数值也全错）。

1. **时间账**：`循环用时 = Σ(普攻段连段帧)/近战攻速 + 射击次数 × 射击间隔 + 奔袭次数 × (1.2333 / (1 + 技能速度))`。普攻段的 `连段 / 取消` 帧与段内命中数（`格式: "{%}×N"`）都在 `weapon.data.ts` 的「普通攻击」字段里；`ranged::攻速 = 1 / 射击间隔`。
2. **逐秒上限**（决定产能，必须显式建模）：
   - 近战自费掉血：`min(近战命中/s × 5%, 14%/s)`
   - 远程衰朽掉血：`min(触发次数/s, 1) × 10%`（精5 = 每 1.0s 最多 1 次）
   - ⚠️ 上限是**硬约束**：多打不会超过它，扫描曲线上会出现平台期。
3. **换算链**：`灾厄值/s = 掉血% × 1000 + Σ(紊乱消耗层数 × 4) + 武器伤害实例数 × 1`（lv0 每记伤害 +1），`羽化层/s = 灾厄值/s ÷ 100`。⇒ **每秒掉血% × 10 = 羽化层/s**。
4. **触发侧**：`消耗/s = 射击频率 × 每射子弹数 × 多重 + 周期被动齐射频率 × 齐射发数`；`有效羽化 = min(生成, 消耗)`，并记录**受限项**（生成受限还是消耗受限）。
   ⚠️ **多发 / 多段效果的结算次数要按「铺开时间」算，不能按「一次触发」算**：lv5 齐射的 9 发是**按射速连射**的，铺在 2.7s 窗口里 ⇒ 1s 节流的 `衰朽` 在窗口内能结算 **2 次**（不是 1 次）。建模前先问一句「这个 N 发效果是一次性结算还是逐次结算」，差一倍产能。
5. **伤害**：`非灾厄 = (近战总伤 + 命中数 × 执行者附加伤害 + 射击伤害 + 奔袭及被动) / 循环`；`羽化 = 单层羽化 × 有效羽化`。
6. **扫描找最优**（4a 整组 × 收尾残段 × 射击次数 × 奔袭次数），输出 `循环 / 掉血%/s / 生成 / 消耗 / 受限 / 非灾厄 / 羽化 / 综合`。**平台期说明触到了硬上限**——此时报告要点明「上限在哪」，而不是继续调手法。
7. **周期项一律做「双口径对照」再下结论**：作者口径 `触发周期 = ceil(2.7/循环)×循环`（按循环取整）与宽松口径 `min(浴血次数/循环, 1/2.7)` 在**循环落在 2.0~2.7s 时会差 5% 以上**（模型敏感区）。**推荐手法要挑两套口径都稳的那一个**（法露茜实测：循环 2.726s → 71.06 / 71.016 亿，两口径几乎一致；循环 2.416s → 71.888 / 66.013 亿，完全不可比）。只给一套口径的数字很容易被推翻。

> ⚠️ 单层[羽化]伤害、各段近战伤害等**逐项数值必须从真实模型取**（`calculateTargetFunction`），不要用 `customVariables` 里的中间量：那些是作者写死的估算式，参数一改就全错。

### 产出「可导入的 BD JSON」

用户要"新手法 BD / 新构筑 JSON"时，交付物是**站内可直接导入的 `charSettings` JSON**（构筑页「导入」走 `serializeCharSettings` / `normalizeCharSettings`，剪贴板粘贴的就是它，**不带 `title` / `desc` / `id`**）。做法：

1. 以线上那份 `charSettings` 为底（`{...BASE}`），**只换 `customVariables`**，其余配装字段原样保留。
2. 把手法做成**可调旋钮**，且旋钮必须符合游戏可执行性：近战 = `[4a]次数`（1234 整组）＋ `[残段]次数`（收尾 1/2/3 段，各自给 `[残段]用时 / 伤害 / 命中数`），远程 = `[射击]次数`，技能 = `[暗影奔袭]次数`。其余全部由它们派生；`循环用时` 必须由 `用时 × 次数` 组装，别把次数写死进 `[射击]用时`。
3. 用 §3 的逐秒模型把 `循环用时 / 掉血速率(带上限 min) / 生成 / 消耗 / 有效 / 非灾厄 / 羽化 / 综合` 全部翻成表达式，`targetFunction` 保持 `"综合DPS"`。
4. **必须做回环校验**：`JSON.stringify → JSON.parse → normalizeCharSettings → createCharBuildFromSettings().calculate()`，与手算模型逐项对齐（对不上通常是漏了每发子弹数 / 收招帧这类乘数）。落盘 `outputs/`，一条 JSON 单行即可（约 3~4 KB）。
5. 交付说明里给一句**建议标题 / 描述**（发布分享时用），并点明相对线上原版的 Δ%。

> 自定义变量**按名递归求值 + 有循环引用检测**（`CharBuild.evaluateAST` 的 `resolvingVariables`），**写在前面/后面都行**；但解析失败不报错、只在界面上把 `targetFunction` 打回 `伤害`，所以落盘前务必跑一次 `calculate()` 而不是只看中间量。

## 4. 陷阱（都是踩过的）

1. **表达式命名空间失效**：构筑的 `customVariables` 里若有 `羽化::xxx` 这类以**武器名**为命名空间的自定义属性，一旦把对应武器换掉，重算会抛 `无效命名空间: "羽化"`。→ 消融函数必须 try/catch 返回 NaN，并在报告里注明"该项不可比"（这本身也是信息：说明配装是围绕那把武器写的）。
2. **`auraMod: 0` 抛异常**，见 §3 表。
3. ⚠️ **魔灵主动技是计入的 —— 别被那条「写空」的自定义变量骗了**：作者常写 `customVariables["魔灵主动综合提升"] = "1+0.0*0.6"`，看着像"人为归零"，但**主动技本来就由 `petCoverage` 自动计入**（`玛瑙艾尔芙(主动)` 给 `[多重射击]`，覆盖率 60% 时 `ranged::多重` 1.0000 → **1.2500**）。法露茜实测：覆盖率 60% → 0 掉 **1.41%（作者原稿 66.037 亿）/ 1.61%（推荐 BD 71.016 亿）**，满覆盖 +2.36% / +2.71%；被动 **+5.80% / +5.71%**；潜质 4 条 **−12.34% / −12.64%**（脚本 `.tmp/falu-pet-income.ts`）。
   - ⇒ **判据：不要只看 `customVariables` 的系数，要按前端真实数据流复核**（`normalizeCharSettings` → `createCharBuildFromSettings` → 改 `petCoverage` / `petId` / `traits` 重算）。曾因「表达式系数 = 0 + 覆盖率 0→1 无变化」就断言"主动技没进公式、是白给的收益空档"，**是错的** —— 那次"无变化"是因为没走到注入主动 BUFF 的那条路径。
   - 反向也小心：主动既已自动计入，再把它写进自定义变量就是**重复计算**。
4. **`traits` 存的是 `[bid, 等级]`**（bid 如 1023），不是 `petEntrys` 的 `id`。查潜质名用 `petEntrys.find(x => x.bid === bid)`。
5. **血量参数不要取到机制下限以下**：法露茜这类"自费扣血有下限"的角色，数值最优血线可能低于游戏机制下限（如模型里 25% 比 30% 高 6.58%，但 30% 才是可达下限）。报告时必须区分「数值最优」与「实战可达」。
6. **系列互斥**：`CharBuild.exclusiveSeries` = `indepSeries + ["囚狼1","换生灵","海妖","审判者","巨鲸","金乌","焰灵","黄衣","夜使"]`。同系列只能带一件。**非互斥系列可以叠多件**（夜魔、冥犬、契约者、囚狼 实测可 6/5/4/3 件）。检查配装合规性时按实际件数统计一次。
7. **触发率允许溢出 100%**：`触发率 = 武器基础触发 × (1 + 加成池)`，**加成池来自魔之楔 / BUFF，不含武器自身 / 熔炼的 `加成.触发`**（`getWeaponFullness` 只调 `getTotalBonus`）。溢出部分 × 充盈转化 = 角色充盈威力（见 `CharBuild.getWeaponFullness` / `getFullnessWeaponSources`）。实测一把武器能到 180%~204%。
8. ⚠️ **`resonanceGain` 是「和鸣增益」，不是「溯源」**（i18n `char-build.resonance_gain`）。它进入 `攻击 / 生命 / 护盾 / 防御 = 基础 × (1 + 加成池 + 和鸣增益)`（`CharBuild.ts:1184-1187`），与溯源无关。**扫描 `resonanceGain` 得到的是"和鸣增益每点收益"**；模型里的**溯源以 BUFF 形式表达**（如 `法露茜4溯` / `法露茜6溯`），要测溯源就在 `buffs` 里按名字增删。这两者曾被混为一谈，出过一版错标。
   ⚠️ 它的**可选档位只有 `0 / 0.5 / 1 / 1.5 / 2 / 2.5 / 3`**（`CharInputNode.vue` 的 `SelectItem` 列表，默认 `3`），
   **满值就是 3、不存在更高档**，随队伍固定、**不是可培养项** —— 报告里不能把它排进「养成优先级」。曾把上限当成 6 排过优先级，出过一版错标。
9. **技能威力有生命依赖，堆技能威力 ≠ 技能流**：法露茜的技能倍率挂**最大生命**（浴血 = `6.6 × 生命 × 技能威力`），而生命大头来自武器（血染织羽 **+300% 生命**）。实测远程换技能向武器 + 角色槽 8 格全堆技能威力（面板 676%），DPS 反而从 5.16 亿掉到 **1.41 亿** —— 技能威力上去了、生命被挤掉，技能侧自己先崩。真正的"技能流"是**换辅助**（见 §3），不是换武器或单项堆属性。
10. **`customVariables` 是构筑作者手写的估算式，不是游戏公式**。像 `(1+2219/740)` 这种把觉醒值倍率写死的项，改参数不会动。解读伤害来源时可以用它拆分，但不要把式子本身当成机制说明。
11. **技能威力有边际拐点**：实测某条"技能效益"词条换成"充盈威力"反而 **+7.61%**。堆到一定值后要横向比同槽位的其他取向，别只看单条 Δ 排序。
12. ⚠️ **周期型被动的「最短间隔」只节流它自己那条路径**：血染织羽 lv5 的 `最短间隔 = 消耗层数 × 0.9s`（3 层 = 2.7s）只约束「**消耗紊乱时齐射额外子弹**」；**手动射击是另一条独立路径**（lv0「此武器子弹造成伤害时，消耗 1 层[羽化]」），逐颗子弹实时触发、**没有周期上限**。拿 2.7s 去限制手动射击会把掉血与羽化产能一起压死。
13. ⚠️ **但反过来，别把「一次触发」当成「一次结算」**：lv5 齐射的 9 发是按射速**连射**的，铺在 2.7s 窗口里 ⇒ 1s 节流的 `衰朽` 在窗口内结算 **2 次**。作者 `每秒掉血百分比 = 0.14 + [衰朽]系数*0.1*2/[羽化]触发周期` 里的 **`2` 是机制、不是随手写的假设**：按 2 次算，模型复现 **66.037 亿**，与作者标注**差 0.00%**；按 1 次算只有 58.03 亿（偏差 12%）。
   ⇒ **判据：与作者标注对得上（<0.1%）才说明口径吃对了**；对不上要先怀疑自己的口径，而不是认为作者的数写错了。
14. ⚠️ **手法候选集必须先过「可执行性」**：见 §3 —— 连续按近战键只跑 `1234→1234`，近战只能是 `(1234)^n ＋ 残段`。漏了这条会算出打不出来的"最优解"（曾据此给出 `一二三×2`、`一二段×3` 两版错手法，DPS 也全错）。
15. ⚠️ **先分清一个属性进的是「生成项」还是「只进消耗项」，再下价值结论**：`有效羽化 = min(生成, 消耗)` 取较小值，但**较小值本身是变动的** —— 乘在**生成侧**的属性是**实打实的增产**。法露茜实测 `ranged::多重` 1.00 / 1.25 / 1.50 / 2.00 / 3.00 → 69.889 / **71.016** / 72.143 / 74.396 / 78.903 亿，**线性，每 +0.25 ≈ +1.13 亿**。
    曾因为「消耗 5.04 远大于生成 2.74、消耗不是瓶颈」就断言"再堆多重不抬 DPS" —— **错**。消耗侧宽裕只说明**它不卡**，生成侧的大小照样决定结果。**拿到新机制先定位它落在哪个加数上。**
16. **速率项一律写成「实例数/秒」，不要写「按键次数 × N × 多重」**：两者数值等价但后者口径不清，改手法（多射一枪 / 改齐射发数）时极易漏更新。法露茜范式：`[射击]子弹数 = [射击]次数 × 2 × ranged::多重`（`2` = 武器「射击」技能的**子弹 + 弹射两个字段，各自吃多重** ⇒ 一枪 = 2×多重 颗），生成侧与消耗侧**统一引用同一个 `[远程]子弹每秒`**。
17. **机制上有用 ≠ 配装里塞得进去**：多重对法露茜生成侧敏感，但远程槽逐件换 `叠影`(53005, 多重 1.5) / `叠影·灵巧`(53011, 多重 1.21) **全部为负（−2.9% ~ −30.7%）** —— 换掉任何一件暴击 / 暴伤件，**单层[羽化] 就从 22.23 亿掉到 15.80~19.50 亿**，而多重只换来生成 +0.24~0.30 层/s。⇒ **配装结论必须来自「逐件替换」实验，不能拿敏感性曲线直接推**（另：掉血上限来源件如 `衰朽` 不可换，实验里要显式跳过）。
18. ⚠️ **别把「续航预算类资源」当成「进结算的资源」**：法露茜的 **[神智]** 只是 [伏击] / [执行者] 的**持续时间预算**（进 [潜入夜色] −10、每秒 −10、[暗影奔袭] −20），**不参与任何伤害结算**；真正被「吃掉」的是 **[火属性紊乱] 层数**（被动 [浴血]：`[处决目标] 被 [暗影奔袭] 命中 → 消耗 3 层 → 660% 最大生命火属性范围伤害 + 回复 50% 生命`）。
    另注：**[执行者] 状态下 [潜入夜色] 会被替换成 [暗影奔袭]**（`char.data.ts` 技能描述原文），所以「E 槽」在实战里打的就是这个吃层动作 —— 别按字面把 [神智] 当成被消耗的资源。
    跨作品类比（例：观众视角里「像仆人 Q 清生命之契」）只能类比「**消耗层数 → 范围爆发 + 回血**」这一层，**资源归属是相反的**（仆人清**自己身上**的，法露茜吃**敌人身上**的）。写类比前先查 `src/data/d/char.data.ts` 里该技能的 `描述` / `行为` 原文，不要凭直觉挂资源名。
19. ⚠️ **「消耗 3 层」是单判口径，实战按 6 层算**：`[觉醒]`（310403）的 `消耗[觉醒值]阈值 = 15000`，觉醒值 ≥ 阈值时 `[暗影奔袭]` 是**强化版**（`[暗影奔袭]伤害倍率提升 = 22.19` = +2219% 最大生命）；强化版命中**多判** ⇒ 1 次 `[暗影奔袭]` × **2 判** × 3 层 = **6 层**紊乱 ⇒ `[浴血]` 结算 **2 次**。作者式里的 `[浴血]倍率系数 = 2` 指的就是这个 2 判（**不是**「齐射 2 次」）。照字面用 3 层重算会把紊乱项与灾厄值产能砍掉一半。
20. **术语写进文案时一律走游戏原文**（拿 tag 当依据，别用口语）：`战技`（tag 技能/战技，如 `[潜入夜色]`）、`终结技`（tag 技能/终结技，如 `[坠入黑渊]`）、`普攻`；不要写「E 技能 / 大招 / 平A」。跨作品借词要分侧：原神侧是 `元素爆发`。查 tag：`grep -n 'tag: \["技能"' src/data/d/*.data.ts`。
21. ⚠️ **引用「间隔 / 频率」类机制数字前，先按「溯源」修正过再写**：`char.data.ts` 的角色条目带 `溯源: [...]` 数组（**数组第 1 条 = 1 溯**），很多基础描述里的「每隔 N 秒」是 **0 溯** 口径。法露茜实证：技能描述写「每隔 3 秒，将部分角色攻击力转化为最大生命值」，而 **1 溯 = 「[执行者]状态中，转化攻击力间隔降低50%」⇒ 实际 1.5 秒**；构筑挂 4溯 / 6溯 时 **1 溯 必然在内**，故文案写 3 秒就是错的（模型侧 `法露茜Q` 取满 `mx: 12` 档，正是 1.5s 的密度）。
    查法：`grep -n "溯源: \[" src/data/d/char.data.ts` 读该角色数组，再用 `buff.data.ts` 里同角色的 `N溯` 条目（`法露茜2溯` / `4溯` / `6溯`）**反查编号是否对齐**（数组下标 0/1/3/5 分别对应 1/2/4/6 溯）。
22. ⚠️ **写「两套辅助分别给什么」时，先分清「作用域」，别把通用乘区归给某一侧**。作用域只有三类：
    - **技能侧专属**：技能伤害 / 技能威力 / 技能速度 / 技能无视防御；
    - **武器侧专属**：武器伤害；
    - **通用（两种伤害都全额吃）**：攻击 / 增伤 / 属性穿透 / 背水 / 昂扬 / 属性伤害。
    法露茜实证：武器流辅助（菲娜 + 松露与榛子）7 条增益里**只有「菲娜助战 · 武器伤害 +10%」是武器专属**，其余增伤(+45%/+103%) / 属性穿透(+24%) / 背水(+22%) / 攻击 全是通用乘区；技能流辅助侧的 `昂扬`（扶疏 4 溯、卡米拉助战）与 `卡米拉7溯 · 火属性伤害 +35%` 同理也是通用项。把通用项写成「只加武器伤害」是**口径错误**（会误导配装取向）。
23. ⚠️ **消融「某个队友组」前，先按「BUFF id = 角色 id」把该队友的专属 BUFF 找全**：法露茜实证 —— `榛子大冲击`（背水 +22%）看似中立增益，其实 buff **id = 5101 = `松露与榛子` 的角色 id** ⇒ **松露专属**。只按名字前缀过滤（`/^松露/`）会把它漏掉，得出**只撤 3 条 −30.73%** 的错口径；含它的 4 条才是 **−39.30%**。
    查法：`grep -n '名称: "XXX"' src/data/d/buff.data.ts`，读条目 `id` 再比对该角色 id；归属不明的 BUFF 一律回落到这一步核对，不要靠名称猜。
24. ⚠️ **「换辅助」类结论不要只做「原地逐条替换」**：把 A 辅助的 BUFF 换成 B 辅助的 BUFF、配装与队友武器全不动，会**漏掉 B 自带的武器 / 羽翼·鼓舞 / 助战类增益**，得出严重低估（法露茜实测：武器流 MOD 里把松露组原地换成扶疏组只有 **43.183 亿**，而**线上同作者的「菲娜扶疏」原稿是 63.846 亿**）。
    - 正确做法：**优先拿线上同作者、同配装流派的两份构筑直接对照**（本例 66.037 vs 63.846 亿 = −3.32%），必要时再拆逐条贡献。
    - 换辅助的典型收益方向要**看它给什么乘区，不是看它怎么被触发**：`扶疏被动` 的描述是「自身和队友**释放战技和终结技**后叠 1 层**技能速度**（最多 2/3 层，叠加刷新）」—— 「释放战技 / 终结技」只是**覆盖率条件**（扶疏自己也吃叠层），真正的收益是**技能速度**，而技能速度是**技能出手频率乘区**（`DPS = or(攻速,1+技能速度)×…`）⇒ **战技施放更快**，窗口碎的速切 / 共斗场景里才塞得进伤害（面板 +60.0% → **+101.4%**）。曾按描述里的"触发"字面反推出「开终结技越勤，收益越高」，把**覆盖率条件当成了收益来源**。
    - 同理，队友收益别只算"某个 BD 内各辅助占比"，要按**整队口径全枚举**（`C(4,2)` 双人 ＋ 单人 ＋ 无队友 = 11 组）。法露茜实测 66.037 / 63.846 / 54.730 / 49.274 / 48.423 / 41.128 / 40.082 / 36.538 / 29.424 / 28.357 / 17.435 亿 —— **前三名全带菲娜**，无菲娜天花板 49.274（队友整体贡献 73.6%）。⚠️ 用「固定配装只换队友槽」会严重失真（技能向队友落在武器流 MOD 下只有 **28.655** 亿）。脚本 `.tmp/falu-teammate-matrix.ts`。
25. ⚠️ **算「溯源收益」时，别把「`buffs` 列表里没有」当成「BD 没计入」—— 机制可能写在 `customVariables` 表达式里**：法露茜实证 —— 2 溯（「释放[暗影奔袭]时，若场上仅有一名[处决目标]，对其伤害提升 100%」）**不在 `buffs` 里**，而是被作者写成表达式修饰符 `潜入夜色::[暗影奔袭]伤害**{增伤:+1}**`。只查 `buffs` 就会误判成「条件型、未挂、不计入」。
    - 反例警告：`buff.data.ts` 里**同时存在**一条同名 `法露茜2溯`（**全局增伤 1**）—— 那是给所有伤害 +100%，与原文「**对其**（那一名 [处决目标]）伤害提升 100%」不是一回事；**拿 BUFF 版当 2 溯会把阶梯整体抬高**（曾据此算出虚高的 84.4 亿）。
    - **3 / 5 溯也不是「边际为 0」**：它们抬的是**逐技能等级**（`[潜入夜色]` / `[坠入黑渊]` 各 +2）。设置层虽有单一 `charSkillLevel`，但**拿到 build 后可单独改某个技能的等级**：`build.skills.find(s => s.名称.includes("潜入夜色")).等级 = 10`（`LeveledSkill` 的 setter 会重算 `字段`，效果进 `潜入夜色::[暗影奔袭]伤害`）。实测 3 / 5 溯各值 **+1.0% / +0.9%**，不是 0。
    - 唯一真「没接线」的是 3 / 5 溯里的 **「[觉醒]等级 +1」**：作者表达式把 `[暗影奔袭]` 倍率提升**写死成 `2219`**（= [觉醒] 12 级的值，`char.data.ts` 该字段的 12 项数组末位），只能按「3 / 5 在场 ⇒ 折到 12 级」人工折算（不折算则 3 / 5 溯只有 +0.79% / +0.60%）。
    - **报告口径**：**六溯都要进阶梯**，且阶梯终点必须等于 BD 自身。法露茜：43.554 → 48.816 → 49.207 → 49.708 → 53.744 → 54.225 → **71.016** 亿（边际 +12.08% / +0.80% / +1.02% / +8.12% / +0.90% / +30.96%），**六条各有落点、没有一条需要「再叠一次」**；单撤 = −10.27% / −1.00% / −1.04% / −7.51% / −0.89% / −23.64%。**阶梯失配就说明漏了落点**，别用「条件型不计入」把它糊过去。
26. ⚠️ **口播 / 文案里不写实现细节**（表达式、字段名、`customVariables`、`{增伤:+1}` 之类）：那些是**核数用的证据**，只进技术附录（脚本的附 B）。旁白要落到「机制 + 数字」上；**同一件事在小步位上不必单独展开** —— 法露茜 2 溯只加强化战技（`[暗影奔袭]`）那一段，属小步，和 3 / 5 溯并列一句「各自只值 0.8% ~ 1.0%」即可，不需要为它解释实现方式。

27. ⚠️ **自写 MOD 合法性校验时，`excludeSeries` 与 `weapon.类别` 都是「计算属性」，原始 `modMap` / `weaponMap` 里没有这两个键**：
    - `mod.excludeSeries` 在 `LeveledMod` 上（`囚狼 && id>100000 → ["囚狼1"]`；`换生灵/海妖 → ["换生灵","海妖"]`；其余 → `[系列]`）。直接 `modMap.get(id).excludeSeries` 得到 `undefined` ⇒ **系列互斥会静默全通过**，搜索器会产出 `百首×4 + 狮鹫×2` 这种不可用配装。
    - `weapon.类别` = `weaponData.类型[1]`（双刀/长剑/太刀/重剑/长柄/鞭刃）。漏读会**整类丢掉「武器类别限定」MOD**。
    - **中枢 = 系列 `羽蛇`**（前端 `modOptions.filter(o => o.ser === "羽蛇")`），共 35 件（11 通用 + 7 属性 × 4），`最大耐受` 17/30/55 三档；**中枢同样吃属性限制**（给风角色装 `背水(火)` 完全无效）。所以「普通槽池排除羽蛇、中枢槽只收羽蛇 + 过属性」才是正确口径。
    - 实测锚点（线上 9 角色 36 份构筑）：能叠的系列只有 `契约者/冥犬/夜魔/囚狼/邪龙`，**全都不在 `exclusiveSeries` 里**；互斥系列叠放出现 **0 次**。
28. ⚠️ **`autoBuild` 不做耐受上限校验**：它只保证「填满 `ModTypeMaxSlot` 格 + 名称/系列互斥 + 属性/限定过滤」。输出必须自己复核 `build.getModCostMax(tab) <= build.getModCap(tab)`（角色槽 cap = `20 + 中枢.最大耐受 + charLevel`）。另外 `Σ ceil(耐受/2)` 只是**下界**（实测 下界 109 / 实算 154 / 上限 155，含异极性 ×1.5 惩罚），**下界不超 ≠ 可行**。想「带着必带件填空」：把必带件放进 build 槽位，同时列进 `includeTypes` 与 `preserveTypes`。
29. ⚠️ **同一效果别算两遍：易伤是独立乘区，不是 `增伤` 池**。「受到来自本角色的伤害提高 62%」这类**没有 `tag` 的说明性字段**内核不会自动结算，要在表达式里写 `×(1+0.62)`；**不要**同时塞进 `customBuff: [["增伤",0.62]]` —— 那是加进增伤池（只值 +19.9%）且与表达式重复，实测**虚高 1.83 倍**。判据：回环校验（落盘 JSON 重算）对不上、且「撤该项」的落差 ≠ 理论值，就是重复计算。
    同理，**技能文本里的状态加成（如某 Q 12 级「攻击速度 +0.51 / 背水 +0.2」）属属性池，放 `customBuff` 是对的**；「追猎/匿踪状态下才生效」的状态覆盖率要自己在手法建模里处理（按次数上限或摊销折算）。
30. 需要「从零推一套最优构筑」的完整流程（读机制 → 辅助排列组合 → buff 组 → 定计算方向 → 魔灵潜质 → 必带 MOD → `autoBuild` → 消融）见本机技能 **`.agents/skills/build-creator/SKILL.md`** 与它的 `example/` 脚本骨架（通用、无角色内容，spec 驱动）。

## 5. 概念口径（角色机制→模型字段，写攻略前先对一次）

数值结论要落到游戏术语上，先把术语与模型字段对齐，否则容易"数字对、说法错"。

| 术语 | 在模型/数据里的落点 |
|---|---|
| **充盈威力** | 角色属性。= Σ 角色 MOD 词条（如 `充盈·巧力` 金 = 5.5） + Σ 各武器 `max(0, 触发率 − 100%) × 充盈转化`。转化 = 基础 1 + 该武器作用域 MOD 转化（如 `缠缚·满溢` +2）。单位是比例：16.52 = 1652% |
| **充盈伤害** | 字段 `tag` 含 `[充盈]` 的伤害整体 **× (1 + 充盈威力)**（`CharBuild.ts:3222`）；`转充盈: X` 则 × (1 + X × 充盈威力) |
| **灾厄值 / 羽化** | 灾厄武器熔炉机制：造伤 +1 灾厄值（上限 200）、每损失 0.5% 最大生命 +5 值 → 满 100 → 1 层羽化（≤10 层）→ 子弹命中消耗 1 层 → 500% 灾厄伤害 + 80% 最大生命，**两者都带 `[充盈]` 标签** |
| **属性紊乱** | 挂在敌人身上的属性异常层数（火属性角色 → 火属性紊乱）。消耗它是多个被动的触发器（魔之楔 `焚炎紊乱` 增伤、武器熔炉给灾厄值/技能速度/额外子弹等）。**模型没有独立的紊乱字段**，作者的 `customVariables` 用 `min(...)` 把它折成了灾厄值的产能上限——报告时要说清"消耗频率即产能约束"，不要编造层数上限 |
| **掉血上限** | [羽化] 产能的物理天花板，两条独立：近战（[执行者] 双刀「每击自费 5% 最大生命」）封顶 **14%/s**；远程（魔之楔 `衰朽` 精5「远程武器伤害时生命 ≥35% 流失 10%，每 1.0s 最多 1 次」）封顶 **10%/s**。合计 **24%/s** ⇒ 2.4 层羽化/s |
| **[羽化]触发** | 两条路径**独立且节流不同**：① lv0 —「此武器**子弹**造成伤害时，消耗 1 层[羽化]」→ **手动射击逐颗实时，无周期**；② lv5[血染·趋光] —「**消耗紊乱**时发射 消耗层数×3 发额外子弹，最短间隔 消耗层数×0.9s」→ 不射击才会被这条卡住。⚠️ 这 9 发**按射速连射**、铺在 2.7s 窗口里 ⇒ 1s 节流的衰朽结算 **2 次**（一次齐射 = 2 次衰朽，占满 0.73/1.0 的额度 ⇒ **手动射击 1 次/循环 就够顶满 10%/s**） |
| **近战连招** | 连续按攻击键只跑 `1234 → 1234`，**不能只打前两段再从头**；所以近战序列只能是 `(1234)^n ＋ 收尾残段`。扫描手法时这是硬候选集约束 |

## 6. 批量采集线上构筑快照（写攻略 / 汇总配装素材时）

要写「某角色线上都怎么配」这类内容，**必须拉全量构筑做统计，不能凭印象**。

```graphql
# 列表（找该角色所有构筑）
builds(charId: $id, limit: 100, sortBy: "likes") {
    id title desc charId views likes isRecommended isPinned createdAt updateAt user { id name }
}
# 详情（配装全量在 charSettings 字符串里）
build(id: $id) { ...同上 + charSettings }
```

⚠️ 口径与坑：
- **时间一律用 `updateAt`**（作者最后一次修改），**不要用 `createdAt`** —— 6 月建、9 月改的构筑是新的，用创建时间会把它当过时货。
- **`isRecommended` / `isPinned` 优先**：站方推荐 / 置顶的构筑要先看，它们通常就是该角色的标准答案。
- **站内链接**：`https://dna-builder.cn/char/<charId>/<build.id>`（`build.id` 是 10 位短码，注意含 `_` / `-`）。可直接给用户，返回 200。
- **MOD 计数必须按「构筑」去重**：`charSettings.modVariants` 里的配置 B/C 与顶层 `charMods` / `meleeMods` / `rangedMods` / `skillWeaponMods` 是**同一批槽位的多套配置**（变体键是中文 `角色` / `近战` / `远程` / `同律` + `中枢`）。逐槽累加会得出 `23/10` 这种超过总数的份数 —— 要先把每份构筑的槽位收进 Set 再计数。
- **魔灵 / 潜质多数只能从 `buffs` 反推**：`petId` 常为 `0`（老构筑根本没存），潜质在 BUFF 里叫 `魔灵潜质:<潜质名>+<档>`，魔灵被动 / 主动叫 `<魔灵名>` / `<魔灵名>(主动)`。只用 `traits` / `petId` 会得出"0 份登记"的错误结论。
- **老构筑会带解析不到的 id**（旧版本 MOD / 武器已从数据包移除）→ 单独标记忽略，不要算进"未登记"。
- ⚠️ **份数少的时候，「多数派」不一定是「共识」**：同一角色的几份构筑可能**方向完全相反**（实测：奥特赛德 2 份 = 灾厄双枪流 vs 射击/近战流，武器 0 重合）。
  此时**只报真正重叠的槽位**当共识（本例：中枢 + 角色 4 件 + 远程 6 件 + 队友），武器/流派要**按方向分开讲**，别合并成一句"主流配装"。
- ⚠️ **站内已存在「AI 驱动生成」的构筑**：`build.desc` 里会自带「本构筑由 AI 驱动生成」字样。转载/引用时必须一并说明来源性质，不要当成人肉实测推荐。
- ⚠️ **`hpPercent` 填 0.01 与 0.25 是等效的**（血量区在 0.25 处已钳制）⇒ 两份构筑血量身位看着差很多，**实际背水身位相同**，不要当成"口径差异"写进分歧。
- 解码用 `charMap` / `modMap` / `weaponMap` / `petMap`（都是 Map，`.get(id)` 取 `.名称`），潜质用 `getPetTraits()`（按 `bid` 匹配槽位里的基础潜质 id，档位 = 等级）。
- 产出两份产物：**逐份明细**（标题 / 更新时间 / 面板口径 / 完整配装 / BUFF）＋ **频次统计**（各槽位 Top，带 `m/N`）。写文案时以统计说"主流 / 分歧"，以明细说"哪一份是什么口径"。

## 7. 报告口径

- 数字统一换算成「亿」并保留 3 位小数；Δ% 一律相对基线。
- 必报：综合 DPS、伤害构成分项与占比、环境口径（防/抗/等级/血线/溯源）。
- 复现校验：**先确认模型算出的基线与作者标注值一致**（偏差 >0.1% 说明 charSettings 没吃干净），再往下做消融。
- 消融表格放"附 B 数值明细"，视频/文章正文只挑权重最高的 5~8 条。
- 交付**分镜脚本**时：每个镜头给「时间轴 · 画面 · 旁白 · 字幕 · 音效」，另附口播全文与数值口径备注（校对用、不进片）。
  时间轴用中文口播速率 **4.7 字/秒** 估：把每镜旁白塞进数组跑一遍 `.tmp/*-timing.mjs` 统计字数并累加，别手估。
  单镜旁白超过 ~250 字就拆成 A/B 两段（25~55 秒/镜），否则配音与画面都对不上。
